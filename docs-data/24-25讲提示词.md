## 第 24 讲：MCP 工具接入（上）—— 搞懂协议，把 Client 跑通

---

### 第一步：理解 MCP 是什么

**做什么**：搞懂 MCP 协议的基本概念。

**目的**：写代码之前先搞清楚这个东西是什么、解决什么问题、和直接调 API 有什么区别。很多程序员拿到需求直接开写，但老师故意先让 Claude 解释概念——自己先理解，再动手。

**设计技巧**：**先问"是什么"，再问"怎么做"。** 面对一个没接触过的新技术，别直接写代码。第一句提示词永远应该是"XXX 是什么？它解决什么问题？"。让 AI 用大白话给你讲一遍，比自己看文档快 10 倍。而且用你的业务场景（智能客服）去问，AI 的回答会更贴合你的需求。

**提示词（老师原话）** ：

> MCP 协议是什么？它解决什么问题？和直接调 REST API 有什么区别？用智能客服的场景帮我解释，重点说清楚为什么需要标准化协议。

---

### 第二步：调研业界真实案例

**做什么**：看一个真实的 MCP Server（Stripe 官方 Server）长什么样。

**目的**：理论懂了，还得看真货。老师选 Stripe 是因为它和智能客服直接相关——支付查询、退款发起。看到真实案例，你才知道"哦，原来 MCP Server 就是暴露这么几个工具"。

**设计技巧**：**学新技术先找一个真实案例看。** 抽象概念难消化，但一个活生生的例子（"Stripe 提供了哪几个工具、怎么接入的"）能让你瞬间理解这东西在真实世界里怎么用。选案例时要选和自己业务相关的，看的时候带着问题："如果我的业务要接，会是什么样？"

**提示词（老师原话）** ：

> 业界有没有真实在用的 MCP Server？给我看一个和智能客服相关的例子，说清楚它提供了哪些工具、怎么接入的。

---

### 第三步：理解 Function Calling 机制

**做什么**：搞懂 LLM 怎么知道要调哪个工具、什么时候调、传什么参数。

**目的**：MCP Client 只负责发请求，决定"要不要调工具、调哪个"的是 LLM。不理解 Function Calling 的交互流程（两次 LLM 调用、tool_calls 消息结构），后面写对话引擎代码时一定会懵。

**设计技巧**：**把黑盒拆开看内部机制。** MCP Client 会调工具不算本事，真正核心的是 LLM 怎么"决定"调工具。老师用三个连续问题（是什么→怎么知道→怎么决定）逼着 Claude 把 Function Calling 的完整时序讲透。以后遇到任何"AI 自动决策"的场景，都可以用这个问法拆解。

**提示词（老师原话）** ：

> Function Calling 是什么？LLM 怎么知道有哪些工具可用？怎么决定什么时候调工具、调哪个、传什么参数？一次用户对话如果需要调工具，完整的交互流程是什么样的？

---

### 第四步：MCP Client 技术选型

**做什么**：调研 Java 生态的 MCP Client SDK，选一个最合适的。

**目的**：老师没用 Spring AI MCP 重框架，选了官方轻量 SDK。原因是 Hify 已有自己的 LLM 调用体系，引入重框架会产生两套抽象互相摩擦。这是"够用就好"的典型决策。

**设计技巧**：**让 AI 做选型对比，同时问"有没有已知问题"。** 技术选型不只是看功能，更要看和自己的现有架构冲不冲突。老师让 Claude 先读项目已有代码再给建议，确保推荐的东西能嵌入现有体系。还特意问了"有没有已知问题"，知道坑在哪比知道怎么用更重要。

**提示词（老师原话）** ：

> Java 生态有哪些 MCP Client 的 SDK？帮我调研主流选项，从成熟度、文档质量、和 Spring 生态兼容性几个维度对比。最后给出建议，Hify 应该选哪个。

---

### 第五步：实现 MCP Server 管理（CRUD + 连通性测试）

**做什么**：在 Hify 里实现 MCP Server 的增删改查，以及连通性测试。

**目的**：这是 MCP 的基础设施——管理接入了哪些 Server，每个 Server 有哪些工具可用。后面 Agent 绑定和对话引擎都依赖这个。

**设计技巧**：**第一个新模块参照已有模块的成熟模式写。** 老师直接说"参照 12 讲 Provider 管理的模式"，因为 Provider 模块已经踩过坑了——CRUD 模式、分页、接口格式全验证过。新模块按同样套路来，Claude 自己去看 Provider 代码就能照猫画虎，你不需要重新规定字段名和代码结构。这是 SDD 的精髓：规范沉淀在项目里，AI 自己会读。

**提示词（Python 版翻译）** ：

> 在 Hify 项目里实现 MCP Server 管理功能。参照 Provider 模块的 CRUD 模式。
>
> 数据表已存在：tb_mcp_server 和 tb_mcp_tool。
>
> 需要做的：
> - ORM 模型、Pydantic DTO、Service 层 CRUD + 分页
> - 连通性测试：向 Server URL 发 JSON-RPC tools/list 请求，成功时解析工具列表写入 tb_mcp_tool（全量替换），失败返回错误信息
> - Router：POST/GET/GET:id/PUT/DELETE + test-connection
> - 删除时检查是否有 Agent 绑定了该 Server 的工具，有则拒绝
> - 注册路由到 main.py
>
> 约束：遵循 CLAUDE.md 规范，ORM 转 DTO，跨模块走接口。

---

### 第六步：Agent 绑定工具

**做什么**：给 Agent 加一个绑定 MCP 工具的接口。

**目的**：管理后台配置 Agent 时能把工具分配给它。后续对话引擎才能知道这个 Agent 可以调哪些工具。

**设计技巧**：**关联表更新用全量替换，别用增量 diff。** 老师在设计里明确用"先删旧再插新"的方式，因为数据量小（最多 10 个），全量替换逻辑简单、不易出错。增量 diff 要考虑新增、删除、保留三种情况，复杂度高很多。小数据量场景，简单粗暴比精巧更好。

**提示词（Python 版翻译）** ：

> 实现 Agent 绑定 MCP 工具的功能。关联表 tb_agent_tool 已存在（字段 agent_id、mcp_tool_id）。
>
> 需要做的：
> - PUT /agents/{id}/tools：接收 tool_ids 数组，全量替换绑定
> - 最多绑定 10 个工具
> - 绑定时校验每个 tool 存在且对应 MCP Server 启用
> - GET /agents/{id} 详情里回填已绑定的 tools 列表（含完整工具信息）
>
> 约束：跨模块调 MCP 走接口，关联表更新用全量替换，ORM 转 DTO。

---

### 第七步：实现 call_tool 方法

**做什么**：实现 McpToolService 的 call_tool 方法，向 MCP Server 发 tools/call 请求。

**目的**：对话引擎调用工具时需要这个方法，先单独实现并验证。

**设计技巧**：**每个可独立运行的方法先单独验证，再嵌入主流程。** 老师把 call_tool 的实现和对话引擎改造拆成两步，因为 call_tool 可以单独用 curl 验证——发一个 tools/call 请求，看返回对不对。验证通过再嵌入对话引擎，出问题就知道是 call_tool 本身的问题还是引擎调度的问题。

**提示词（Python 版翻译）** ：

> 实现 McpToolService.call_tool 方法。参照 test_connection 的 JSON-RPC 调用方式。
>
> 逻辑：根据 tool_id 查工具和所属 Server，向 Server URL 发 tools/call 请求，参数传工具名和 arguments。
> 成功时从 result.content 提取文本返回，JSON-RPC error 或网络异常抛 BizException(MCP_CALL_FAILED)。
> 超时 30s。

---

### 第八步：接入对话引擎

**做什么**：改造 ChatService，让 Agent 能自动调用绑定的工具。

**目的**：让智能客服从"能说"变成"能做"的关键一步。

**设计技巧**：**增量开发三步走，每次都不破坏已有功能。** 老师从 16 讲到现在——基础对话、上下文、RAG、工作流、MCP 工具——每次都只改 ChatService 的一个分支，不改 router 层。测试时也是三步：不绑工具先测原有逻辑没坏 → 绑工具测 Function Calling → 测无关问题不触发工具。每次增量只验证新增的分支，保证旧功能不受影响。

**提示词（Python 版翻译）** ：

> 在对话引擎中接入 MCP 工具调用。只改 send_message 方法内部逻辑。
>
> 流程：
> 1. 加载 Agent 绑定的工具列表，构建 OpenAI 格式的 tools schema
> 2. 有工具且无工作流时，第一次 LLM 调用用非流式（需要拿到 finish_reason 和 tool_calls）
> 3. finish_reason 为 tool_calls 时：解析工具名和参数 → 调 call_tool → 结果追加为 tool 消息 → 第二次流式调用
> 4. finish_reason 为 stop 时：直接推送文本
> 5. 无工具时走原有纯流式逻辑
> 6. 工具调用失败不中断对话，错误喂给 LLM
>
> 约束：适配器需新增 chat_complete 非流式方法支持 tools 参数。跨模块走接口。不改 router 层。

## 第 25 讲：MCP 工具接入（下）—— 自建 MCP Server，让 Agent 能做真正的事

---

### 第一步：理解 MCP Server 代码结构

**做什么**：搞清楚一个 MCP Server 在代码层面长什么样。

**目的**：自建之前先知道要交付什么——它是一个独立应用还是一段代码？和 Hify 什么关系？老师用三层结构解释清楚后，你才知道接下来写的是什么。

**设计技巧**：**动手前先问"我要交付的东西长什么样"。** 和第 24 讲第一步一样——不是直接写代码，而是让 AI 把目标产品描述清楚。这次不是问协议概念，而是问代码结构和部署关系。一个新技术通常需要两次"是什么"：第一次问概念（24 讲），第二次问实现（25 讲）。两次都搞明白了再动手，方向不会偏。

**提示词（老师原话）** ：

> 一个 MCP Server 在代码层面是什么？它是一个独立的应用吗？目录结构长什么样？和 Hify 是什么关系？用三层结构帮我解释。

---

### 第二步：从业务场景推导需要哪些工具

**做什么**：分析用户关于退款会说什么话，从场景推导需要哪些工具。

**目的**：这是整个第 25 讲最有价值的方法论——工具不是拍脑袋定的，是从真实用户诉求推导出来的。老师演示了一个完整的思考流程：用户会说什么 → 每类诉求需要什么能力 → 最后才是"怎么实现"。

**设计技巧**：**从场景推导功能，而不是从技术倒推。** 大部分人做功能是"我能做退款，所以我做退款功能"。老师反过来了——先问"用户会说什么"，再问"需要什么能力"，最后才是"做什么工具"。而且这个过程不是自己想，是让 AI 帮你想，因为 AI 见过的场景比你多，能想到你可能漏掉的诉求。你最后只做决策——AI 推导出四个工具，你拍板用不用。

**提示词（老师原话）** ：

> 我要开发一个退款 MCP Server，供智能客服 Agent 使用。从智能客服的真实场景出发——用户通常会说哪些关于退款的话？每类诉求需要什么样的工具能力？帮我推导出需要哪些工具，每个工具的输入输出是什么。

---

### 第三步：拆解实现步骤

**做什么**：让 Claude 把整个开发过程拆成可独立验证的步骤。

**目的**：大功能拆成小步骤，每步都能验证，出了问题知道在哪层找，不用整个重来。

**设计技巧**：**大任务先拆步骤再写代码。** 不要直接说"帮我做一个退款 MCP Server"，这太笼统了，AI 容易漏东西。而是让 AI 自己把任务拆成小步骤，你检查拆分是否合理，再逐步执行。每步做完都能验证，错一步只重来一步，不会全盘推翻。这就是"分而治之"的工程习惯。

**提示词（老师原话）** ：

> 我要开发一个退款 MCP Server，独立 Spring Boot 应用，用 Java MCP SDK。提供四个工具：check_refund_eligibility、submit_refund、get_refund_status、cancel_refund，操作 refund_application 表。帮我拆解实现步骤，从建项目到能被 Hify 调用，每步给出验证方式。

### 第四步：建表 + 实现退款业务逻辑

**做什么**：新建退款申请表，写四个退款业务方法，纯业务逻辑不涉及 MCP 协议。

**目的**：菜要先能炒出来，再挂 MCP 招牌。业务逻辑独立验证通过后再套协议壳，分层验证，不混在一起。

**设计技巧**：**业务逻辑和协议层分离。** 老师故意把"写业务方法"和"套 MCP 协议壳"拆成两步。因为业务逻辑可以用普通 REST 接口验证（refund router 那 5 个接口），验证通过再套协议壳。如果混在一起写，出问题你不知道是业务逻辑错了还是协议格式错了。分层验证，每层独立。

**提示词（Python 版翻译）** ：

> 在 Hify 里实现退款业务逻辑模块。
>
> 需要做的：
> - 新建 tb_refund_application 表（order_id、user_id、amount、reason、status、reject_reason）
> - app/refund/ 模块：models、schemas、service、router
> - RefundService 四个方法：check_eligibility、submit_refund、get_status、cancel_refund
> - status 英文存、status_label 中文返给 LLM 读
> - Router 提供 5 个接口（含 reset 清空测试数据）
> - 注册到 main.py

### 第五步：套 MCP 协议壳

**做什么**：给已实现的退款业务方法包装成 MCP 协议端点。

**目的**：Hify 的 MCP Client 能通过 tools/list 发现工具、tools/call 调用工具。Hify 不用改任何代码，只换 URL。

**设计技巧**：**标准化协议让调用方和实现方解耦。** 老师反复强调一个点——Server 从模拟换成真实退款服务，Hify Client 一行代码没改。因为两端都只依赖 MCP 标准协议，不依赖对方的具体实现。你换一个 Server，只改数据库里的一条 URL 记录。这就是为什么要用标准协议而不是直接调 API。

**提示词（Python 版翻译）** ：

> 把 app/refund/ 里的退款业务逻辑包装成 MCP 协议端点，让 Hify 能把它当成标准 MCP Server 调用。
>
> 参照 app/mcp/service.py 里对 JSON-RPC 协议的处理方式。
>
> 要求：
> - 新建路由处理 tools/list 和 tools/call
> - tools/list 返回四个退款工具的 schema，description 写清使用场景
> - tools/call 调 RefundService 对应方法
> - 业务异常走 JSON-RPC error，不抛 HTTP 500
> - 注册到 main.py

### 第六步：MCP 调试工具（前端）

**做什么**：在 MCP Server 详情页加一个调试 Tab。

**目的**：以后每接新 Server，先在调试工具里验证工具行为，再接入对话引擎。形成固定开发流程：工具自身跑通 → 调试工具验证 → 接入 Agent → 端到端测试。

**设计技巧**：**把重复操作变成工具。** 接第一个 Server（模拟订单）时，大家手敲 curl 调试，很痛苦。接入第二个 Server（退款）之前，老师先花时间做调试工具——因为不是只接这一次，以后还有库存 Server、工单 Server、物流 Server。把重复劳动固化成工具，一次投入，长期受益。这就是工程思维——遇到重复操作别忍，立刻做成工具。

**提示词（Python 版翻译）** ：

> 给 MCP 模块做前端管理页面，并在详情页加一个调试工具 Tab。
>
> 后端新增 POST /api/v1/mcp-servers/{id}/debug，复用 call_tool，返回 result 和 elapsed_ms。
>
> 前端：参照 Provider 做列表页和表单。详情页新增"调试"Tab——左侧工具列表，右侧根据 inputSchema 动态渲染参数表单，调接口展示结果和耗时，保留最近 5 次记录。

### 第七步：Agent 绑定退款工具 + 端到端对话验收

**做什么**：把退款工具绑定到 Agent，用真实对话验证 Function Calling 全链路。

**目的**：第 25 讲最终验收——用户说"我要退款"，Agent 自动调 check_refund_eligibility → submit_refund，完整闭环。

**设计技巧**：**验收要按用户真实说话方式测，不按程序员思维测。** 老师给的测试用例不是"调 check_refund_eligibility 传参 order_id=xxx"，而是"我买的商品有质量问题，我要退款"——这就是用户真正会说的话。用真实场景验收，才能发现工具 description 写得好不好、参数设计合不合理、LLM 能不能正确判断什么时候调哪个工具。

> - Agent 绑上四个退款工具
> - 场景验收：发起退款、查进度、撤销、无关问题不触发工具
