# Hify 扩展路径规划

## 当前状态（Phase 0）

```
部署形态：单实例，Docker Compose
用户规模：20-50 人
峰值 QPS：3-5
瓶颈：LLM 外部 API 延迟，不是并发
```

---

## 三阶段扩展路径

| 阶段 | 目标用户 | 触发条件 | 核心改动 |
|------|----------|----------|----------|
| **Phase 1** | 50 → 500 | 响应变慢，CPU/内存持续告警 | 多副本 + 读写分离 + CDN |
| **Phase 2** | 500 → 2000 | LLM 调用队列堆积，P99 > 2s | MQ 异步化 + Qdrant 迁移 + 分库 |
| **Phase 3** | 2000 → 几千 | 模块发布频率互相干扰，资源消耗不均 | 微服务拆分 + API Gateway + Redis 集群 |

---

## Phase 1：多副本 + 读写分离

**目标：** 50 → 500 人，垂直扩展 + 基础高可用

### 触发条件

```
docker stats 显示 CPU / 内存持续告警
或
响应时间明显变慢
```

### 改什么

| 组件 | 改动 | 说明 |
|------|------|------|
| **FastAPI** | 从 1 副本扩到 2-3 副本 | 负载分担 |
| **MySQL** | 加读写分离（一主一从） | 读请求分流到从库 |
| **静态资源** | 上 CDN | 首屏加载加速（Nginx gzip 已做） |
| **会话存储** | 进程内内存 → Redis | 多实例共享会话，解决 SSE 连接粘性 |

### 不改什么

- 整体单体架构不动
- Qdrant 不变（我们从一开始就用独立 Qdrant，不像老师要从 pgvector 迁移）
- Redis 单节点不动（Phase 2 再主从）
- 同步调用方式不变（SSE 继续用）

### 关键技术点：SSE 连接粘性

**问题：** 多副本后，负载均衡会把用户的 SSE 对话随机分发到不同实例。

**解决：** Redis 会话共享 + Nginx ip_hash

```nginx
upstream hify_backend {
    ip_hash;  # 同 IP 路由到同一实例
    server backend1:8000;
    server backend2:8000;
    server backend3:8000;
}
```

用户对话期间，Nginx 把请求路由到同一实例，SSE 保持稳定。

## Phase 2：MQ 异步化 + 分库

**目标：** 500 → 2000 人，解决 LLM 调用瓶颈

### 触发条件

```
LLM 调用队列堆积，对话成功率下降
或
知识库检索 P99 > 2s
```

### 改什么

| 组件 | 改动 | 说明 |
|------|------|------|
| **LLM 调用** | 引入消息队列（Kafka/RocketMQ） | 削峰填谷，异步处理 |
| **前端** | SSE → 轮询或 WebSocket | MQ 异步化后，同步 SSE 不再适用 |
| **MySQL** | 按业务模块分库 | chat_db / agent_db / provider_db |
| **Qdrant** | 确认集群模式 | 向量库高可用 |
| **Redis** | 主从复制 | 缓存高可用 |

### 不改什么

- Spring Boot / FastAPI 仍是单体，不做微服务拆分
- Redis 架构（Phase 2 开始做主从，但不改集群）
- Qdrant 架构不动

### ⚠️ 重要：这是 Breaking Change

**MQ 异步化带来的代价：**

```
Phase 1: 前端用 SSE 接收实时流式响应
Phase 2: 前端需要改成轮询或 WebSocket

SSE → 轮询/WebSocket 是 breaking change
改动成本不低，所以不到触发条件不做
```

**为什么是 breaking change：**
- SSE 是服务器推送，MQ 异步化后服务器不再"推"，客户端需要主动拉
- 前端需要重写流式接收逻辑
- 交互方式变了，用户体验不同

**决策原则：** 不到万不得已，不做这个改动。Phase 1 的并发控制 + 断路器能撑一段时间。

### 架构图（Phase 2）

```
用户浏览器
    │
    │ WebSocket / 轮询（不再是 SSE）
    ▼
Nginx
    │
    ▼
FastAPI（单体）
    │
    ├── /api/* → 同步处理（管理请求）
    │
    └── /chat/* → 发到 MQ 队列 → LLM Consumer → WebSocket 推送
                        ↑
                        │
                   ┌────┴────┐
                   │  Kafka   │
                   └─────────┘
```

## Phase 3：微服务拆分

**目标：** 2000 → 几千人，按模块独立部署

### 触发条件

```
某一模块的发布频率互相干扰
或
某一模块（如 Agent 执行）资源消耗远超其他模块
```

### 改什么

| 组件 | 改动 | 说明 |
|------|------|------|
| **服务拆分** | 按模块拆分为独立服务 | Chat / Agent / Provider / Knowledge / Workflow / MCP 各自独立 |
| **路由** | 引入 API Gateway（替代 Nginx） | 统一路由 + 鉴权 + 限流 |
| **Redis** | 换集群模式 | 缓存水平扩展 |
| **服务间通信** | REST → gRPC | 更高效的内部调用 |
| **事务** | 引入 Saga / TCC 模式 | 解决分布式事务问题 |

### 不改什么

- MySQL 主从架构不动
- Qdrant 不动
- K8s 编排层不动（继续用）

### 关键技术点：服务接口的价值

**为什么 Phase 1 要设计"跨模块走 Service 接口"？**

就是因为这一步：

```
拆分前：chat.service → agent.service（本地调用）
拆分后：chat.service → agent.grpc（远程调用）

接口签名不变，只需要改依赖注入配置
```

**详见：** `CODE_ORGANIZATION.md` 的 interfaces.py 设计

|------|----------|----------|

## 注意事项

1. **触发条件驱动** — 不提前做，等问题真实出现再动
2. **Phase 2 的 Breaking Change 要谨慎** — SSE → WebSocket/轮询 成本不低，能用 Phase 1 的方案撑住就先撑
3. **监控先行** — 每个阶段前确保有足够监控数据支撑决策
4. **保持接口设计** — 为 Phase 3 微服务拆分预留空间
