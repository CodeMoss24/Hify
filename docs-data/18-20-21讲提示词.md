## 2. 行为层：用时间线描述动态交互

**做什么：** 按时间顺序一步步描述“用户点发送后，页面接下来几秒内发生什么”，而不是简单的“点按钮→弹窗→保存”。包含 SSE 用 `fetch` 不用 `EventSource`、Markdown 渲染、智能滚动等技术约束。

**目的：** 对话页面的交互是连续的，不是离散的。用“四维度描述”会漏掉大量行为细节。时间线描述能覆盖每一步的交互状态变化，并把容易踩坑的技术约束在描述里显式说明。

**提示词（Python 版本）：**

> 布局正确，现在实现对话页面的行为逻辑。按时间线逐步描述：
>
> **发送消息的完整时间线：**
> 1. 用户在输入框输入内容，点击发送按钮（或按 Enter 键）
> 2. 输入框立即清空，发送按钮变为不可点击状态
> 3. 消息区域底部出现用户消息气泡（靠右对齐，深色背景）
> 4. 紧接着出现 AI 消息气泡（靠左对齐，浅色背景），显示加载动画
> 5. 前端用 **fetch** 手动处理 SSE 流式响应（**不要用 EventSource**，因为接口是 POST 请求）
> 6. 每收到一个 SSE chunk，把 content 追加到 AI 气泡，自动滚动到底部
> 7. 收到 done 事件后，移除加载动画，恢复发送按钮
> 8. 如果收到 error 事件或网络失败，AI 气泡显示红色错误提示，按钮恢复
>
> **技术约束：**
> - SSE 流式响应用 `fetch` + `ReadableStream` 手动解析，不用 `EventSource`
> - AI 回复内容支持 Markdown 渲染（引入 `marked` 库）
> - 新消息追加时自动滚动到底部，但用户主动向上滚动查看历史时不强制滚动
> - 输入框支持 Enter 发送、Shift+Enter 换行
>
> **需要创建的文件：**
> - `hify-web/src/views/chat/ChatView.vue`：对话页面主组件
> - 如果会话列表的 API 文件还不存在，补充 `hify-web/src/api/conversation.ts`

## 2. 数据管线处理逻辑

**做什么：** 实现文档处理五步管线——解析文本（TXT/MD 直接读，PDF 用 PyPDF2）→ 分块（递归分割，chunk_size=512 token，overlap=64 token）→ 向量化（调 `LlmClient.embed()`）→ 存储（Qdrant + MySQL）→ 更新状态（DONE/FAILED）。上传文档后自动异步触发。

**目的：** 让上传的文档自动完成从原始文件到可检索向量化数据的全部处理。这是 RAG 最核心的数据管道。

**提示词（Python 版本）：**

> 在 Hify 项目里实现文档处理数据管线。技术栈：Python FastAPI + SQLAlchemy + Qdrant + 火山引擎 Embedding。
>
> **1. 创建 `app/knowledge/pipeline.py`，实现 `DocumentPipeline` 类：**
> - `run(self, db, document_id)`：串联五步。任何一步失败 → status=FAILED，写 error_message。全部成功 → status=DONE，chunk_count=实际分块数
> - Step 1 - `_parse_text`：TXT/MD 直接读，PDF 用 PyPDF2。解析失败写 error_message
> - Step 2 - `_split_chunks`：chunk_size=512 token，overlap=64 token。切割优先级：段落 > 句子 > 字符截断
> - Step 3 - `_embed_chunks`：调 `LlmClient.embed()`（已实现），补上 embedding 字段（1024 维）
> - Step 4 - `_store_chunks`：Qdrant collection `knowledge_chunks`（维度 1024，Cosine 距离）+ MySQL `DocumentChunkModel`
> - Step 5 - `_set_failed` / 更新状态为 DONE
>
> **2. 修改 `app/knowledge/service.py`**：`upload_document` 末尾启动异步任务 `asyncio.create_task(pipeline.run(db, doc_id))`
>
> **约束**：每个环节独立方法，管线只负责串联和状态管理。向量维度 1024。不引入新的大型依赖。

## 4. 接入对话引擎（RAG 检索）

**做什么：** 在 `send_message` 的拼装 messages 步骤前，检查 Agent 是否绑了知识库。如果有，把用户问题向量化 → Qdrant 检索 → 检索到的 chunk 拼进 System Prompt。格式为：原始 Prompt + 参考资料 + "如果资料中没有相关信息，直接说没有找到相关资料，不要编造"。

**目的：** 让绑了知识库的 Agent 回答时能引用文档内容。没绑知识库的 Agent 不受任何影响。这是最小侵入的接入方式——只改 `build_messages` 方法，其他八步不动。

**提示词（Python 版本）：**

> 修改 `app/chat/service.py` 的 `send_message` 方法，在拼装 messages 数组时插入 RAG 检索结果。
>
> **改动范围：只改 `send_message` 这一个方法，不要动其他任何代码。**
>
> **具体逻辑：**
> 1. 在步骤 4（拼装 messages）之前，通过 `self._agent_service.get_knowledge_base_ids(db, agent_id)` 获取 Agent 绑定的知识库 ID 列表
> 2. 对每个知识库调 `DocumentChunkService.search_chunks`：将用户消息 `embed` 生成向量 → Qdrant 检索（Top-3，相似度阈值 0.3）→ 返回匹配的 chunk 列表
> 3. 把检索到的 chunk 拼进 system prompt：
>    ```
>    {Agent 原始 Prompt}
>
>    请基于以下参考资料回答用户问题。

>
> **约束**：不要修改流式调用、SSE 转发、消息存储的逻辑。不要改 Controller 层。Agent 原始 Prompt 要保留，参考资料附在后面。`search_chunks` 方法调 Qdrant 的 `search` 接口，用余弦相似度。
