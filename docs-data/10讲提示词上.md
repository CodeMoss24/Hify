### 1. 数据库初始化脚本（建表 DDL）

**做什么**：生成全部 18 张业务表的建表 SQL 脚本。

**目的**：MySQL 里还没有表，业务代码跑不起来。先把所有表的 DDL 生成好，一键执行建表。

**提示词**：

---

### 2. 数据库模型集中导入

**做什么**：在 `app/main.py` 里 import 所有业务模块的 models。

**目的**：SQLAlchemy 启动时只会发现被 import 过的模型。如果某个模块的 models 从来没被引用过，对应的表就不会被 `create_all()` 创建。集中 import 一次，确保 18 张表全部被发现。

**提示词**：

> 请确认 `app/main.py` 里有没有导入所有业务模块的 models。如果没有，帮我在 `app/main.py` 里补充 import 所有业务模块的 models（provider、agent、chat、mcp、workflow、knowledge），确保 SQLAlchemy 启动时能发现全部 18 张表。只补 import，不写业务逻辑。

---

### 3. 并发控制模块

**做什么**：创建 `LlmExecutor`（LLM 调用并发控制）和 `AsyncExecutor`（后台异步任务执行器）。

**目的**：LLM 调用是慢活儿（3-30 秒），不能让它占着 FastAPI 的主事件循环。用 Semaphore 限制同时调 LLM 的并发数，用 `asyncio.to_thread` 把同步阻塞操作丢到独立线程。后台任务（如文档向量化）同样限制并发，防止打爆 CPU。

**提示词**：

> 在 `app/common/` 下创建 `executor.py`，实现 Hify 的并发控制模块。要求：
> 1. 创建 `LlmExecutor` 类，用于 LLM 调用的并发控制：用 `asyncio.Semaphore` 限制全局 LLM 并发数为 10，调用 LLM 时使用 `asyncio.to_thread` 将同步阻塞操作丢到独立线程池执行，保护 FastAPI 主事件循环不阻塞，记录每次调用的耗时和异常到日志。
> 2. 创建 `AsyncExecutor` 类，用于后台异步任务（如文档向量化）：同样用 `asyncio.Semaphore` 限制并发数为 5，提供 `submit()` 方法接收一个函数放入后台执行，不阻塞主流程。
> 3. 所有线程池和信号量参数从 `.env` 文件读取，默认值对齐 CLAUDE.md 的配置。不引入 Celery 或其他第三方任务队列。

### 4. Base 统一基类

**做什么**：把所有 ORM 模型需要的公共字段（`id`、`created_at`、`updated_at`、`deleted`）和公共方法（`find_all()`、`soft_delete()`）合并到 `Base` 一个类里。

**目的**：18 张表每一张都需要这四个公共字段。写在 Base 里一次，所有业务模型只继承 Base 就能自动带上去，不用每张表重复写，也不会漏。

**提示词**：（这一步是逐步演化来的，最终形态是 Provider 样板创建时的指令）

**提示词**：

### 6. 入参校验

**做什么**：在 Provider 模块的 `schemas.py` 里，用 Pydantic 的 `Field` 给创建和更新接口的入参加上校验规则（name 必填、provider_type 只能在四种里选、base_url 必须是合法 URL 等）。

**目的**：在数据进入 Service 层之前拦住非法输入，不让脏数据流到数据库层。校验失败时，FastAPI 自动抛出 `RequestValidationError`，由 `handlers.py` 里已有的异常处理器捕获并转成标准错误响应。

**提示词**：

> 在 `app/provider/schemas.py` 里，为 Provider 模块的创建和更新接口定义请求 DTO，加上入参校验规则：
> 1. `ProviderCreate`（创建用）：`name` 必填，最小长度 1，最大 64；`provider_type` 必填，只能是 `openai`、`anthropic`、`gemini`、`ollama` 四种之一；`base_url` 必填，合法的 URL 格式；`api_key` 必填，最小长度 1。
> 2. `ProviderUpdate`（更新用）：所有字段 `Optional`，不传则不更新，传了就按创建规则校验。
> 3. 在 `app/provider/router.py` 的 `POST /providers` 接口里，把 `ProviderCreate` 作为请求体的类型，FastAPI 会自动执行校验。校验失败时 FastAPI 抛出 `RequestValidationError`，由已在 `handlers.py` 注册好的 `validation_exception_handler` 捕获并返回标准错误响应。

### 7. 统一时间序列化

**做什么**：在 `app/common/config.py` 里创建一个时间序列化配置函数，让所有 `datetime` 和 `date` 对象在返回 JSON 时自动转为 ISO 8601 字符串格式。

**目的**：不配这个，FastAPI 返回的时间字段可能带时区偏移量、微秒等，前端解析困难。统一成 `YYYY-MM-DDTHH:MM:SS` 格式后，前端只需要处理一种时间格式。

**提示词**：

### 8. 缓存策略落地

**做什么**：在 `app/common/` 下创建 `CacheHelper` 工具类，封装标准的 Cache-Aside 模式。

**目的**：Provider 和 Agent 配置读多写少，每次都查数据库是浪费。有了 CacheHelper，业务代码只需要调 `cache.get_or_set(key, ttl, factory)`，自动完成“查缓存 → 没命中就查库 → 塞回缓存”的流程。更新或删除时调 `cache.evict()` 失效缓存。

**提示词**：

> 在 `app/common/` 下创建 `cache_helper.py`，封装缓存工具类 `CacheHelper`，实现标准的 Cache-Aside 模式。要求：
> 1. 构造方法接收 `RedisClient` 实例
> 2. 提供 `get_or_set(key, ttl, factory)` 异步方法：先从 Redis 查，命中直接返回；未命中调 factory 查库，序列化 JSON 塞回 Redis，设 ttl 过期时间；factory 返回 None 则不缓存
> 3. 提供 `evict(key)` 和 `evict_pattern(pattern)` 异步方法
> 4. 所有序列化用 `json.dumps`/`json.loads`，不引入新依赖

### 10. LLM HTTP 客户端封装

**做什么**：创建统一的 `LlmClient`，封装所有外部 LLM API 调用（OpenAI、Claude、Gemini、Ollama），支持普通 POST 请求和 SSE 流式请求。

**目的**：不在每个业务模块里散落不同的 HTTP 调用方式。统一管理超时（连接 5s、读 120s）、日志记录（URL、耗时、状态码）、异常分类（超时/认证失败/限流/服务端错误）。

**提示词**：

> 在 `app/infrastructure/llm/` 下创建 `llm_client.py`，封装统一的 LLM HTTP 客户端。要求：
> 1. 内部持有 `httpx.AsyncClient`（普通请求，连接超时 5s，读超时 120s）和 `aiohttp.ClientSession`（SSE 流式请求，连接超时 5s，读超时 0）
> 2. 提供 `post(url, headers, body) -> dict` 和 `stream(url, headers, body, callback)` 两个核心方法
> 3. 所有请求记录日志，异常统一转为 `LlmApiException`（区分 TIMEOUT、AUTH_FAILED、RATE_LIMITED、SERVER_ERROR 四种类型）
> 4. 创建 `LlmApiException` 类，继承 `BizException`，携带 `ErrorCode` 和原始异常 `cause`

### 11. 熔断与重试

**做什么**：为 LLM 调用加上熔断器和重试处理器。每个 LLM Provider 配独立熔断器，连续失败 5 次熔断，30 秒冷却后半开探测。重试按异常类型区分：超时/5xx 退避重试，429 限流退避重试，401/403 认证失败不重试。

**目的**：某个 LLM Provider 挂了之后，系统不会傻傻地反复发请求等 60 秒超时。熔断器自动切断请求，保护系统资源。重试只针对“暂时性”的失败，认证类失败不重试。

**提示词**：

> 在 `app/infrastructure/llm/` 下创建 `circuit_breaker.py`，为 LLM 调用增加熔断与重试机制。要求：
> 1. `CircuitBreaker` 类：按 `base_url` 隔离，连续失败 5 次熔断，30 秒冷却后半开探测，探测成功恢复，失败重新熔断
> 2. `RetryHandler` 类：超时/5xx 退避重试（1s→2s→4s），429 退避重试（2s→4s，上限 30s），401/403 不重试
> 3. 集成进 `LlmClient`：`post()` 和 `stream()` 执行前检查熔断器状态，已熔断快速失败；只有可重试异常计入熔断器失败计数，401/403 不触发熔断
> 4. 不引入新依赖，用 `asyncio` 和 `time` 实现

---

### 12. 结构化日志与请求追踪

**做什么**：配置统一的日志系统，开发环境控制台彩色输出，生产环境 JSON 格式文件滚动存储（按天滚动，保留 30 天）。每个请求自动生成 `traceId`，串联同一请求的所有日志。

**目的**：出了问题不再大海捞针。搜一个 traceId，这个请求从进入中间件到 Controller 到 Service 到数据库到 LLM 调用，整条链路一目了然。超过 1 秒的慢请求自动标 WARN。

**提示词**：

> 在 `app/common/` 下创建 `logging_config.py`，实现结构化日志与请求追踪。要求：
> 1. 开发环境控制台彩色输出，生产环境 JSON 格式输出到文件，按天滚动，保留 30 天
> 2. 使用 FastAPI 的 `@app.middleware("http")` 创建 `RequestLogMiddleware`，每个请求自动生成 `traceId`（UUID4），记录 method、path、status_code、耗时，超过 1 秒的慢请求标 WARN
> 3. 将 `traceId` 通过 `ContextVar` 注入日志上下文，让同一请求的所有日志自动带上同一个 `traceId`，请求结束时清理
> 4. 在 `app/main.py` 中集成：导入并调用 `setup_logging(app)`，注册请求日志中间件
> 5. 不引入新依赖，用 Python 标准库 `logging` 和 `uuid` 实现
